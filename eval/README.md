# eval/ — 評価基盤

動画解析の手法・プロンプト・モデル・パラメータを比較するときの標準手順と、そのためのツール群。
本ディレクトリはスキル本体（`skills/agentic-video-analysis-skill/`）には含めない。
配布されるのはスキルだけで、評価基盤は開発・回帰確認のためにこのリポジトリに残す。

`eval/fixtures/` は git 管理外。動画そのものと、それに対する正解データ（ground truth）は
各自ローカルで用意する。ここに置くのは正解データの作り方・照合ルールの書き方・採点スクリプトの
使い方であって、特定の動画やその正解データそのものではない。

```text
eval/
  README.md                    このファイル
  score.py                     正解データ照合・網羅率・カテゴリ別・誤認数・コスト集計
  union_recall.py              複数実行の和集合網羅率
  ground_truth.example.json    正解データの雛形（抽象的な例。このファイルの §10 と対応）
  fixtures/                    実データ置き場（git 管理外。各自ローカルで用意）
    <name>/
      video.mp4                （任意。無くてもよい。パスの記録用）
      gt/                       正解データ作成中に切り出したタイル・クロップ画像
      ground_truth.json         正解データ本体
```

---

## 1. 位置づけ

このスキルは「動画をタイル化 or ネイティブ動画理解で反復解析し、見どころ候補やタイムラインを
出す」ものだが、**出力が良いかどうかは出力を眺めるだけでは分からない**。プロンプトや既定値
（fps、モデル、範囲の切り方など）を変えるたびに、同じ動画・同じ正解データで測り直す必要がある。
`eval/` はそのための場所であり、スキルの実行そのものには関与しない。対象読者は、このリポジトリの
プロンプトや既定値を変更する開発者。エンドユーザーが動画解析を使うだけなら触る必要はない。

---

## 2. 大前提: モデル出力同士を比べても優劣は決まらない

一番やりがちな失敗は、**手法 A の出力と手法 B の出力を並べて「B の方が詳しそう」と判断する**
ことである。これは機能しない。理由は 3 つ。

1. **どちらも間違っているケースを検出できない。** 同じ場面を、ある手法は「事象 X」、別の
   手法は「事象 Y」と書くことがある。正解データが無ければ、どちらが正しいか永久に決まらない。
2. **詳しい出力が正しい出力とは限らない。** 出力が長い手法は、正しい記述も誤った記述も
   同時に増やしやすい。件数だけ見ると「詳しい方が良い」と誤解する。
3. **もっともらしい嘘は人間の目視をすり抜ける。** そのドメインで自然に聞こえる記述（そのドメインで
   登場しがちだが実際の映像には映っていない要素の言及など）は、映像を見ずに読むと疑う理由が無い。

**最初に人手で正解データを作る。** ここに全体の作業時間の半分を使ってよい。正解データさえ
あれば、以降の比較は自動化できて、何度でも再利用できる。

---

## 3. 全体の流れ

```text
Step 1  正解データを人手で作る          ← 一番重要。手を抜かない
Step 2  照合ルールを正解データに埋め込む
Step 3  比較条件を決める（変数は1つだけ）
Step 4  各条件を3回以上実行
Step 5  採点する（網羅率・カテゴリ別・誤認数・コスト）
Step 6  記録して再現可能にする
```

---

## 4. Step 1: 正解データを人手で作る

### 4-1. まず動画の素性を確認する

```bash
ffprobe -v error -show_entries format=duration \
  -show_entries stream=codec_name,width,height,r_frame_rate,nb_frames \
  -of default=noprint_wrappers=1 eval/fixtures/<name>/video.mp4
```

長さ・解像度・fps・**音声トラックの有無**を確認する。音声を扱えない手法（フレーム抽出系）と
扱える手法（ネイティブ動画理解）を比べるなら、音声の有無は結論を左右する。無音でないことも
確認しておく。

```bash
ffmpeg -i eval/fixtures/<name>/video.mp4 -af volumedetect -f null - 2>&1 | grep mean_volume
```

### 4-2. 全編をラベル付きタイルにして自分の目で見る

fps=3 で全編をタイル化し、**自分の目で全部見る**。

```bash
python skills/agentic-video-analysis-skill/scripts/tile_video_frames.py \
  --video <video> --start 0 --end 9 --fps 3 --frames-per-tile 28 \
  --output eval/fixtures/<name>/gt/gt_0_9.jpg
```

`--start` / `--end` を変えながら全区間を出力する。

- **fps=3 が出発点。** 1 秒未満の出来事（短い視覚効果、色の切り替わりなど）は fps=1 では
  タイルに現れず、正解データから消える。
- 1 タイル 24〜28 セル、1 タイルあたり 8〜9 秒が読みやすい。
- セルラベルの `t=<秒>s` が絶対秒になっていることを確認する。ここがずれると全部ずれる。

### 4-3. 画面上の状態表示の読み方を決めて記録する

多くの映像では、画面上の数値・アイコンなどの状態表示が最も信頼できる根拠になる。どこに何が
出るかを最初に決めて、正解データの `hud_notes` にメモしておく。

```json
"hud_notes": "状態表示Aは画面左下、状態表示Bは画面右下に表示される。"
```

数値やアイコンが読めない場合は該当フレームを切り出して拡大する。タイルのセルサイズでは
潰れる要素（小さいアイコンの種類の同定など）は必ずこれをやる。

```bash
ffmpeg -v error -ss 34.0 -i eval/fixtures/<name>/video.mp4 -frames:v 1 \
  -vf "crop=280:200:0:0,scale=560:400" -q:v 2 eval/fixtures/<name>/gt/crop_34.jpg -y
```

### 4-4. 争点になりそうな箇所は fps を上げて再確認する

fps=3 では**因果関係を取り違える**ことがある。前後 0.3 秒で意味が変わる場面は fps=8〜10 で
見直す。例えば、fps=3 では「発光 → 直後に数値減少」に見えた場面が、fps=8 で見直すと実際には
「発光は別の事象（状態表示の更新演出）」で、数値減少の原因は別のタイミングの接触だった、
ということが起こりうる。

**この種の訂正は、モデル出力との食い違いから見つかることが多い。** Step 5 でモデルが正解
データと違うことを言い出したら、**まずモデルを疑う前に正解データを疑う**。正解データも
人間が作った以上、間違う。

### 4-5. 事象を原子的な単位で書き出す

1 出来事 = 1 エントリ。まとめない。

- NG: 「接触して状態が悪化する」
- OK: 「接触（状態表示A 05→02）」＋「状態変化1」＋「状態変化2」を別エントリに分ける

各エントリに持たせる項目:

| 項目 | 内容 |
|------|------|
| `id` | `E01` のような固定 ID。以降ずっとこれで参照する |
| `start` / `end` | 絶対秒 |
| `cat` | カテゴリ（後述） |
| `name` | 短い名前 |
| `evidence` | **画面に何が映っているか**。解釈ではなく観察を書く |

### 4-6. カテゴリを付ける

全体の網羅率だけ見ると、「導入部を細かく書いただけの手法」が高得点になってしまう。カテゴリ
別に見れば、**編集価値のある事象を取れているか**が分かる。目安となる 4 分類:

| | 内容 | 編集価値 |
|---|------|---------|
| A | 導入・演出（読み込み画面、場面紹介、開始前カウントダウンなど） | 低 |
| B | 状態変化（数値・順位・残量などの変化） | 中（文脈） |
| C | 操作・技術（意図的な操作による加速・回避・特殊アクションなど） | **高** |
| D | 異常・事故（衝突・落下・失敗・中断など） | **高** |

カテゴリ名・境界は動画のドメインに合わせて調整してよいが、「編集価値が低い/高い」の軸は
残すこと。C・D 相当のカテゴリの網羅率が実質的な評価指標になる。

### 4-7. ネガティブコントロールを明示的に列挙する

**「存在しないことを確認したもの」を書き出す。** これが誤認率の測定を可能にする。

```json
{
  "name": "そのドメインで登場しがちだが映像には無い要素の出現",
  "pattern": "架空要素A|特殊出現物X",
  "verdict": "誤り",
  "evidence": "全編を通じて該当の視覚要素は一度も表示されない"
}
```

ネガティブコントロールの作り方は 2 通り。

- **事前**: そのドメインで誤認されやすいもの（そのドメインで登場しがちだが実際の映像には
  無い要素・キャラクター・アイテム・状態など）を先に列挙する
- **事後**: モデルが言い出した固有名詞・状態を映像で確認し、否定できたら追加する

`verdict` は `誤り` と `根拠なし` を分ける。「難易度が高い設定である」は映像から判定できない
だけで、誤りとは限らない。この 2 つを混ぜると誤認率が過大に出る。

## 5. Step 2: 照合ルールを正解データに埋め込む

採点を人間の判断でやると再現性が無く、条件が増えたときに破綻する。**正解データそのものに
照合ルールを持たせる。**

```json
"match": {
  "window": [33.6, 35.0],
  "any": ["接触", "衝突", "停止", "エフェクト", "減少"]
}
```

判定は「出力エントリの `[start, end]` が `window` と重なり、かつ `name + evidence` が `any`
のいずれかにマッチしたら検出」とする。

- `window` は正解の秒数に**前後 0.5〜1 秒の余裕**を持たせる。境界の厳密さを測りたいわけでは
  ないので、狭くしすぎない。
- `any` は**同義の言い換えを網羅**する。「救出」「復帰」「引き上げ」のように表現の揺れを
  広く取る。ここが貧弱だと、正しい出力を取りこぼして手法を不当に低く評価する。
- 似た事象が近接している場合は、キーワードではなく **`window` で分離**する。

誤認は正規表現で走査する。時間帯を限定したいものには `window` を付ける。

```json
{
  "name": "特定の異常状態の発動(30s台)",
  "pattern": "(特殊|異常)状態.{0,6}(発動|発生)",
  "window": [30.5, 33.0]
}
```

ルールを書いたら、**手で採点した 1 件と突き合わせて検算する**。スコアラーのバグは静かに
全条件を汚染する。

## 6. Step 3: 比較条件を決める

### 変数は 1 つだけ変える

「タイル方式 vs ネイティブ動画理解」を比べたいなら、**モデル・プロンプト・出力スキーマ・
反復回数をすべて揃える**。手法の違いに見えたものが、実際にはモデルや経路の違いだった、
という取り違えは起きやすい。

### モデルを差し替える前に測る

モデルの差し替えは「変数を 1 つだけ変える」の典型例で、**手法比較と同じ手順がそのまま
使える**。モデル指定だけを変えて、同じ正解データで採点する。

差し替えの判断で見るのは網羅率だけではない。最低この 4 つを並べる。

| 指標 | 見る理由 |
|------|---------|
| 網羅率の**平均と sd** | 差が sd より小さければ「差が無い」以上のことは言えない |
| **誤認数** | 網羅率が同じでも誤認だけ増えることがある |
| **コスト** | 単価が同じでも、出力が冗長になればコストは上がる |
| **落とす場所** | 平均が同じでも、落ちる箇所が偏るなら性質が違う |

先行検証で確認した教訓:

- 隣接する世代同士のモデル差は、**測っても sd に埋もれて出ないことが多い**。「新しいから
  上げる」だけの差し替えは、精度が変わらないままコストと誤認だけを増やすことがある。
- 世代を 1 つ以上飛ばした差は実在することがある一方、それでもコストや誤認との
  トレードオフは必ず確認する。
- 古いモデルには**機能そのものが無い**ことがある（特定の処理モードに非対応など）。また
  構造化出力が壊れることがあり、範囲ごとの try/except が無いと実行全体が落ちる。

**新しい方が良いとは限らない。** 差し替えは測ってから決める。

### プロンプトを目的と一致させる

**「見どころを数個挙げて」というプロンプトの出力を、網羅率で採点してはいけない。** 指示通り
少数だけ出したモデルが正解の大半を取りこぼすのは当然で、これは手法の欠陥ではない。網羅率を
測りたいなら、プロンプトも「漏れなく列挙せよ」でなければならない。目的が違うプロンプト
（見どころ抽出 用と 悉皆列挙 用）は分けて扱う。

### 出力形式を固定する

JSON スキーマで固定する。自由記述だと、採点が「書き方の違い」に引きずられる。

## 7. Step 4: 各条件を 3 回以上実行する

1 回の結果は偶然を含む。同じ条件でも、ある回では検出できた事象を別の回では丸ごと落とす、
ということが起こる。

- 最低 3 回。結論を分ける重要な条件は 4〜5 回。**差が小さいと予想される比較（隣接世代の
  モデルなど）は最初から 5 回**にする。3 回では sd が安定せず、無い差を有ると読んでしまう。
- **失敗した実行も記録に残す。** API エラーやスキーマ違反の頻度も手法の性質。
- 実行結果は 1 実行 1 セッションで保存し、途中で止まっても再開できるようにする
  （既存の出力があればスキップする）。

## 8. Step 5: 採点する

`score.py` に、実行結果のタイムライン JSON と正解データを渡す。

```bash
python eval/score.py <session>/merge/timeline.json --gt eval/fixtures/<name>/ground_truth.json
```

（`score.py` の細かいオプションは未実装の部分がある。実装時に `--help` を参照）

最低限、次の 4 つを出す。

| 指標 | 見方 |
|------|------|
| **網羅率（recall）** | 正解 N 件中いくつ検出したか |
| **カテゴリ別網羅率** | 編集価値の高いカテゴリ（C・D 相当）が本命 |
| **誤認数** | ネガティブコントロールに引っかかった数 |
| **コスト・レイテンシ** | トークン内訳と金額、実時間 |

出力エントリ数は指標ではなく**参考値**。多いほど良いわけではない。網羅率と誤認数をセットで
見る。

トークンは内訳まで記録する。`input` / `tool_use` / `output` / `thinking` を分けておくと、
「なぜ高いのか」が後から分かる。

複数回実行した結果の**和集合網羅率**（どれか1回でも検出できた事象の割合）は
`union_recall.py` で見る。

```bash
python eval/union_recall.py --gt eval/fixtures/<name>/ground_truth.json <timeline1.json> <timeline2.json> ...
```

先行検証では、同条件で複数回実行して和集合を取ると単発実行より網羅率が上がることを確認
している。**見逃しは事象ごとにランダムに起きやすい**ため、複数回の和集合は有効な打ち手になる。

---

## 9. Step 6: 記録して再現可能にする

正解データには次を必ず書く。

- `built_by`: どうやって作ったか（fps、拡大確認の有無など）
- `built_at`: 作成日
- `revision_note`: **訂正履歴**。いつ何をなぜ直したか

正解データは一度作れば同じ動画で何度でも使える。プロンプトや既定値、モデルが変わったら、
条件を足して再実行するだけでよい。

---

## 10. 正解データの JSON 形式

`ground_truth.example.json` を参照。トップレベルのキーは次の通り。

| キー | 内容 |
|------|------|
| `video` | 動画のパス（記録用。相対パスで書く） |
| `duration_sec` | 動画の長さ（秒） |
| `built_by` | 正解データの作成方法（fps、拡大確認の有無など） |
| `built_at` | 作成日 |
| `revision_note` | 訂正履歴。いつ何をなぜ直したか |
| `hud_notes` | 画面上の状態表示の位置・読み方 |
| `categories` | カテゴリ ID → 説明のマップ |
| `events[]` | 事象のリスト（下記） |
| `negatives[]` | ネガティブコントロールのリスト（下記） |

`events[]` の各要素:

| キー | 内容 |
|------|------|
| `id` | 固定 ID（例: `E01`） |
| `start` / `end` | 絶対秒 |
| `cat` | カテゴリ ID |
| `name` | 短い名前 |
| `evidence` | 画面上の観察事実 |
| `match.window` | `[start, end]`。照合時の余裕を含んだ秒範囲 |
| `match.any` | 検出とみなす言い換えのリスト（いずれかにマッチすれば検出） |

`negatives[]` の各要素:

| キー | 内容 |
|------|------|
| `name` | 短い名前 |
| `pattern` | 誤認を検出する正規表現 |
| `window`（任意） | 時間帯を限定する場合の `[start, end]` |
| `verdict` | `誤り`（映像で否定できる）または `根拠なし`（映像から判定できないだけ） |
| `evidence` | 否定・判定不能の根拠 |

## 11. チェックリストとよくある落とし穴

### チェックリスト

正解データ:

- [ ] 全編を fps=3 以上のタイルで自分の目で見た
- [ ] 状態表示の位置と読み方を記録した
- [ ] 争点になる箇所を fps=8 以上で再確認した
- [ ] 事象を原子的な単位に分けた
- [ ] カテゴリを付けた
- [ ] ネガティブコントロールを列挙した（`誤り` と `根拠なし` を分けた）
- [ ] 照合ルール（`window` + `any`）を埋め込んだ
- [ ] スコアラーを手採点 1 件で検算した

比較条件:

- [ ] モデル・プロンプト・出力スキーマを揃え、変数を 1 つに絞った
- [ ] プロンプトの指示と採点指標が一致している
- [ ] 各条件 3 回以上実行した（差が小さい比較は 5 回）
- [ ] モデルを差し替えるなら、網羅率・sd・誤認数・コスト・落とす場所の 5 つを並べた
- [ ] 失敗した実行も記録した

報告:

- [ ] 網羅率をカテゴリ別に出した
- [ ] 誤認数を出した
- [ ] トークンを内訳付きで出した
- [ ] 価格の仮定（tool-use トークンの扱いなど）を明記した
- [ ] 限界（動画本数、試行回数など）を書いた

### よくある落とし穴

| 落とし穴 | 何が起きるか |
|---|---|
| 正解データを fps=1 で作る | 1 秒未満の出来事が正解データから消え、それを検出できた手法が「誤検出した」と誤って減点される |
| モデル出力を見てから正解データを書く | モデルの言い分に引きずられる。**先に正解データを固定してから**実行する。実行後の訂正は必ず映像で確認し、履歴を残す |
| キーワードを厳しくしすぎる | 1 語だけを条件にすると、同じ事象を別の言葉で正しく書いた出力を落とす。言い換えを広く取る |
| 網羅率だけで判断する | 導入部を細かく書くだけで低編集価値のカテゴリを埋められる。編集価値の高いカテゴリを見る |
| 1 回の実行で結論を出す | 分散が大きい。特に「見逃し」は再現性が低い |
| コストを total トークンだけで見る | 入力・出力・思考・tool-use で単価が違う。内訳を取る |
